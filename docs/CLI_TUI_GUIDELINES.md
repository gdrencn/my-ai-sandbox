# CLI 与 TUI 交互开发规范

## 1. 用途与适用范围

本文为 Linux CLI 与终端文本用户界面的通用交互指导方针，供不同项目和会话明确引用。它不是项目需求文档，不规定业务功能、技术栈、依赖选择、权限策略、安装方式或发布流程。

本文区分三种界面：

- CLI：通过命令、参数和选项执行操作的命令行接口。
- 内联 TUI（终端文本菜单）：在普通终端输出中显示和刷新当前交互区域，保留已有终端历史。
- 全屏 TUI：接管终端显示区域，通过页面、面板或控件组织交互。

项目决定是否提供菜单、采用哪种 TUI、支持哪些语言以及具体入口形式。仅适用于某类界面的要求，不应机械套用到其他界面。

使用时先阅读本文，再结合项目需求执行。本文不自动加载，需由会话明确引用。

### 优先规则：冲突先讨论

**本规则优先于本文后续的具体交互规范：与项目要求存在冲突时，先指出差异并讨论，再实施涉及冲突的部分。**

- 明确说明冲突的项目要求、本文对应条款及不同选择对交互行为的影响，不自行选择一方后直接实施。
- 用户明确要求优先。若用户已明确确认该冲突的处理方式或例外，直接遵循已有决定，不重复询问。
- 尚未明确的冲突只暂停受影响的部分，不阻止已经授权且不依赖该决定的工作。
- 将确认后的项目例外记录在项目文档中；不因单个项目的例外擅自修改本通用规范。

## 2. 命令行接口

- 命令、参数和选项命名应简洁、语义明确。同类操作保持一致的命名、参数顺序与选项含义。
- 帮助信息说明用途、必填参数、可选参数、默认行为和必要的使用示例。
- 区分交互执行与非交互执行。非交互环境中，不应启动无法操作的菜单或无限等待输入；缺少必要输入或授权时，应给出明确结果。
- 提供正确、可预测的退出码，便于脚本判断成功、失败和中断。取消的退出语义应一致并有说明。
- 标准输出用于命令结果，标准错误用于诊断。提供结构化输出时，不得将进度、提示或诊断混入结果数据。
- 供程序消费的字段、标识符和状态值应稳定，不能因界面语言切换而任意改变。

## 3. 菜单结构

- 按用户任务组织菜单，避免没有实际作用的中间层。
- 菜单标题说明当前位置；选项说明将执行的动作或进入的页面。
- 主入口使用“退出”，下级页面使用“返回”，中止当前输入或操作使用“取消”。三者的行为应与措辞一致。
- 菜单选项逐行排列、左对齐。
- 返回上级时，尽可能保留之前的选中位置；原选项消失时，选择合理的有效位置。
- 条件性选项的显示或禁用应采用一致规则。禁用时，应能让用户理解原因。
- 获取状态失败不能被当作正常空结果，也不能据此宣称全部对象处于正常状态。

## 4. 导航与输入

- 同一程序的同类控件使用一致的按键约定，并显示必要的操作提示。
- 菜单和单选、多选列表使用 ↑／↓ 移动，支持首尾循环。该规则不要求普通文本滚动视图循环。
- 菜单使用 Enter／→ 确认，Esc／← 返回或取消。
- 文本输入中的 ←／→ 用于移动光标，不能同时承担页面返回；Enter 提交，Esc 取消。提示应准确反映当前控件的按键行为。
- 全屏 TUI 中，按键按当前焦点控件解释；面板切换与控件内部导航不能发生未说明的冲突。
- 单选控件明确显示当前选择。多选控件分别表达光标位置和勾选状态，并说明如何勾选及提交。
- 默认值、留空含义及取消方式必须清楚，不让用户猜测回车的后果。
- 输入编辑应正确处理光标移动、插入、删除和多字节字符。
- 正常结束、取消、异常和中断后，都应恢复程序修改过的终端输入模式、光标状态和显示模式。

## 5. 信息展示与选择

- 选择时需要的信息，尽可能直接呈现在选项中，避免先显示完整列表，再重复展示同一组选择项。
- 如果完整信息无法合理合并进选项，可以保留独立详情或表格，但应明确其与选择项的对应关系。
- 多列选项采用一致的列结构，并左对齐。显示状态列时，各行都应有该列；没有值时使用明确的占位表达。
- 使用按终端显示宽度计算的空格对齐，正确处理中文、多字节字符和颜色控制序列，不依赖固定 tab 宽度。
- 颜色只作辅助，不能成为表达状态、选中或错误的唯一方式。
- 界面应适应窄终端及窗口尺寸变化。必要信息不得因截断而失去含义；需要时提供换行、详情或滚动查看。
- 动态标签、名称和输入回显中的控制字符应妥善处理，避免被解释成终端控制指令而破坏布局。

## 6. 操作流程与输出顺序

- 用户选择功能后，应明确感知已进入该功能，不能让新操作的输出看起来属于上一菜单。
- 按“功能说明或标题 → 必要输入 → 执行反馈 → 结果 → 后续导航”的顺序组织交互；没有实际作用的步骤可以省略。
- 先展示操作结果，再展示后续导航。内联菜单不能先刷新父菜单，再把上一操作的结果追加到其后。
- 标题、输入提示、执行反馈、结果和菜单之间的空行采用统一规则，避免紧贴或连续堆积空行。
- 成功、失败、取消和空结果都应有明确反馈，不能留下无法判断是否完成的界面。
- 是否需要停留查看结果，依据内容和任务决定；既不能让重要结果一闪而过，也不要增加无意义的“确认”或“返回”步骤。
- 嵌入交互式子程序时，退出后的去向及收尾流程由项目明确规定，并向用户提供一致体验，不在通用规范中固定为返回菜单或结束程序。

## 7. 进度与结果

- 高频正常进度原地刷新，不持续逐行刷屏。
- 操作结束后保留最终结果；分阶段任务保留有意义的阶段总结。
- 警告、错误和需要用户处理的信息不能被进度刷新覆盖。全屏界面也应提供可回看的结果或诊断区域。
- 清楚区分进行中、中间步骤完成、整体完成和部分失败，不提前宣称全部成功。
- 长时间操作应提供可理解的反馈；无法提供真实百分比时，可显示当前步骤和等待时长，不伪造进度。
- 能取消的操作应说明取消方式；收到取消请求不等于底层操作已经终止，反馈必须反映实际状态。
- 重定向输出时使用普通文本，不输出光标控制序列，也不机械保留每次进度刷新。
- 输出应保留有用的原始诊断。界面层不得为了整洁而隐藏失败原因，或用笼统提示替代可用于判断问题的内容。

## 8. 文案与确认

- 提示明确说明用户需要做什么，避免仅显示内部参数名或模糊标题。
- 说明必要的输入约束、默认值和留空行为，避免用户提交后才获知本可提前说明的要求。
- 确认提示说明操作对象和后果。有破坏性的确认默认采用保守选项，取消不得被解释为同意。
- 确认项使用明确措辞，不能依靠颜色或位置暗示后果。CLI 与菜单对同一操作的确认语义保持一致。
- 错误信息尽可能说明问题及可行的下一步，不虚构原因、不承诺未经确认的恢复结果。
- 部分成功时，分别说明已完成与未完成的内容，以及哪些部分需要用户处理。
- 同一概念使用相同称呼，避免不同入口使用不同术语。

## 9. 国际化与终端兼容

- 本程序拥有的界面文案集中管理，与业务逻辑分离；语言标识和术语保持一致。
- 支持哪些语言、默认哪种语言、何时选择语言，由项目决定。
- 命令、路径、标识符和适合保留的技术术语不强行翻译。
- 外部程序原始诊断不擅自改写或翻译；需要补充说明时，应与原始内容明确区分。
- 正确处理不同语言的字符宽度和文本长度，不能只依据一种语言的显示效果确定布局。
- 内联菜单仅刷新当前交互区域，不清屏、不清除滚动历史、不接管全屏。
- 全屏 TUI 可以管理整个界面区域，但进入和退出时应正确恢复终端；重要结果和诊断应有明确的查看方式。

## 10. 交互验收

根据实际提供的功能，验证下列适用项目：

- 命令帮助、参数错误、退出码、结果数据与诊断分离。
- 按键导航、首尾循环、默认选择、多选状态、返回位置、空列表和条件性选项。
- 文本输入编辑、默认值、取消、确认及非交互执行。
- 功能进入体验、标题与空行、结果与后续导航的顺序。
- 正常进度刷新、阶段总结、最终结果、警告与错误保留。
- 窄终端、尺寸变化、多字节字符、颜色和无控制序列的重定向输出。
- 多语言文案、术语一致性及语言切换后的布局。
- 正常结束、异常、中断及子程序返回后的终端恢复。

终端交互应使用真实终端或 PTY 验证，不能仅检查函数返回值。未提供的控件或界面模式不要求为了满足检查项而额外实现；未验证的兼容性应明确记录。
