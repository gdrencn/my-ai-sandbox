# 代码开发原则

## 用途与适用范围

本文为与项目、编程语言和界面形式无关的代码开发指导原则，主要强调复用、模块化以及调用边界。本文中的模块是具有明确职责和接口的代码单元，可以由函数、类或包表达，不要求每个模块对应一个独立文件。

本文由会话明确引用后使用，不自动加载，也不替代项目需求。与 CLI/TUI 交互规范一样，先作为当前基线使用，后续根据实际使用中发现的问题讨论并完善，不预先扩充没有实际需求的规则。

### 优先规则：冲突先讨论

**本规则优先于本文后续的具体原则：与项目要求存在冲突时，先指出差异并讨论，再实施涉及冲突的部分。**

- 明确说明冲突的项目要求、本文对应条款及不同选择的影响，不自行选择一方后直接实施。
- 用户明确要求优先。若用户已明确确认该冲突的处理方式或例外，直接遵循已有决定，不重复询问。
- 尚未明确的冲突只暂停受影响的部分，不阻止已经授权且不依赖该决定的工作。
- 将确认后的项目例外记录在项目文档中；不因单个项目的例外擅自修改本通用原则。

## 1. 复用优先

- 同一种能力应有统一实现，各处通过调用复用，不重复编写。
- 开发新功能前，先检查已有模块能否满足需求。
- 改进共享能力时，修改其所属模块，让调用方共同受益，不在各处分别修补。
- 复用依据职责和语义，而不只是代码形式相似。

## 2. 为复用划分模块

- 将可独立描述、可重复使用的基础能力抽成模块。
- 模块围绕明确职责组织，提供清楚的调用接口。
- 模块自行管理职责范围内的实现细节，调用者不需要了解或重写这些细节。
- 模块粒度以职责清晰、便于复用为准，避免过大的混合模块，也避免没有实际意义的碎片化拆分。

## 3. 通过组合实现功能

- 较复杂的功能应通过调用基础模块组合实现。
- 组合本身如果成为可复用能力，也可以封装为更高层模块。
- 多次执行相同操作，应重复调用同一模块，不另写一套实现。
- 不为了方便而绕过模块接口、操作其内部实现。

## 4. 明确调用边界

调用模块时，自然存在“调用前、模块执行、调用后”三个位置，但这不意味着每个功能都要建立三阶段框架。

- 被调用模块负责完成自身承诺的能力。
- 调用者负责为何调用、何时调用、提供什么输入，以及如何使用结果。
- 调用前后的逻辑如果属于被调用能力本身，就应放回该模块，不能要求每个调用方重复补齐。
- 如果属于调用者自己的业务，则留在调用者。
- 多个调用方重复出现的调用前后逻辑，应检查是否需要形成共享模块或更高层组合。

## 5. 保持模块独立

- 模块接口明确说明输入、输出、必要条件及失败行为。
- 模块尽量不依赖某个特定调用入口或使用场景。
- 依赖通过清楚的接口表达，减少隐式共享状态和跨模块修改。
- 模块内部调整不应无故要求所有调用方同步修改。

## 6. 抽象保持适度

- 抽象服务于明确的职责和复用需求，不为了显得通用而增加复杂结构。
- 不同语义的功能不应仅为消除几行重复而强行合并。
- 优先选择容易理解、容易验证、容易修改的组织方式。
- 新增逻辑时，先判断它属于哪个模块，再决定写在哪里。
